🇮🇳 The Lens That Matters Most

This review is written for one user: a catalog manager at a mid-size Indian brand, managing 2,000 SKUs across Amazon, Flipkart, and Meesho, running operations from a Windows laptop, on a 4G connection, with a sale event in 48 hours. They are not a designer. They are not a developer. They are tired, slightly panicked, and they need the UI to tell them exactly what is wrong and exactly how to fix it — in plain language, without ambiguity.

  • They expect to see numbers in INR (₹), not USD or unitless values
  • They will paste data from Tally, Excel, or WhatsApp — the UI must be forgiving
  • They use Chrome on Windows — mobile is reference, not primary workflow
  • Technical jargon (DLQ, VERSION_CONFLICT, entity_type) must never reach them
  • They will judge the product on two questions: "Does it tell me what's wrong?" and "Does it tell me how to fix it?"

02 Design Findings 10 issues across 6 screens, ranked by seller impact
🏥
No "Seller Command Centre" — the dashboard is a data table, not a decision surface
SCREEN: Dashboard · ALL SELLERS · First impression
Critical
The dashboard shows stats + a product list. What it doesn't answer: What needs my attention right now? A seller arriving at 9am has one question: "What is broken, and on which channel?" The current layout treats a product with 3 Amazon errors the same as a healthy product. There is no visual triage. The seller has to read every row. At 1,000 SKUs, this is unusable.
Fix Replace the generic stats strip with a "Today's Action Required" panel. Segment products into: Blocked (errors blocking publish), At Risk (warnings that caused rejections in this category before), and Ready. Sort the product list by worst channel health first, not by creation date. Add a single "Fix All Amazon Issues" entry point above the list.
🔤
Technical error language reaches the seller ("VERSION_CONFLICT", "DLQ", "entity_type")
SCREEN: Product Edit · Bulk Import · Error States
Critical
The concurrency conflict path surfaces a "VERSION_CONFLICT" error. The dead-letter queue is labelled "DLQ" in UI. The audit log references "entity_type". These are internal system identifiers — they are meaningless and anxiety-inducing to a catalog manager. When a seller's edit fails because someone else saved first, the message they need is: "Someone else updated this product while you were editing. Here's what changed. Reload to see the latest version." Not a 409 code.
Fix Create a plain-language error message map. Every system error code must have a seller-facing translation. "VERSION_CONFLICT" → "This product was updated by [user] while you were editing." "Dead letter" → "These rows couldn't be fixed automatically. Review them below." "entity_type" should never appear in the UI at all.
📊
Bulk import progress has no real-time feedback during the 18-second benchmark window
SCREEN: Bulk Import · Job Status
Critical
The 1,000-SKU benchmark completes in ~18 seconds. The UI shows job status (completed / retrying / dead_letter) and counters. But there is no live progress animation. From the seller's perspective, they upload a file, see "processing", and wait. If nothing moves for 18 seconds they will assume it has crashed and hit refresh — breaking the job. The "process next chunk" button in the web console suggests manual chunk progression may be required in some flows, which is completely unacceptable for production use.
Fix Add a polling progress bar that auto-updates every 1.5 seconds while a job is in progress. Show: rows processed / total, current throughput (rows/sec), estimated time remaining. Remove any manual "process chunk" trigger from the seller-facing flow — that is an internal debug control and must be hidden behind an admin/developer toggle. The seller's job should process automatically end-to-end.
🗺️
Column mapping UI has no visual feedback — sellers don't know if suggestions are correct
SCREEN: Bulk Import · Smart Mapping Step
High
The header-similarity mapping suggestion returns a confidence score, but the spec doesn't describe that score being shown to the user. A seller uploading a file with headers like "prod_name", "SKU_code", "price_MRP" will see suggested mappings but won't know if "prod_name" → "title" is a 98% match or a 45% guess. Low-confidence mappings accepted silently cause 1,000-row imports with systematically wrong data — one of the worst possible outcomes.
Fix Show confidence visually on each mapping: green dot (>80%), yellow dot (50–80%), red dot (needs review, <50%). High-confidence mappings pre-fill and are collapsed by default. Low-confidence mappings are expanded and highlighted with a warning banner: "We're not sure about these — please verify before importing."
🧭
Validation panel is a list — there's no anchor navigation to jump to the broken field
SCREEN: Product Edit · Validation Panel
High
The validation panel lists all issues. The backlog spec says "field anchors" are required in acceptance criteria (P2-US-005). The implementation description doesn't confirm this was built — it only confirms the panel exists and issues are filterable. If clicking a validation issue doesn't scroll the page to the broken input field and highlight it, the seller has to manually hunt for "material_composition" in a form with 20+ dynamic attribute fields. That hunting adds minutes per product, multiplied by 34 errors in the catalog.
Fix Clicking any validation issue must: (1) scroll to the relevant form field, (2) highlight it with a coloured border and pulsing animation, (3) show the remediation text inline below the field. The validation panel click is a navigation action, not a passive display. Test with a timer: a seller should reach any flagged field within 3 seconds of seeing the error.
🇮🇳
No India-specific data formatting — prices show without ₹, HSN codes without digit grouping
SCREEN: Dashboard · Product List · Product Form
High
The canonical model stores MRP, selling_price, and inventory_qty. The implementation shows these as raw values. In India, prices are displayed as ₹1,999 (not 1999 or INR 1999). Large numbers use Indian comma formatting: ₹12,00,000 (not ₹1,200,000). Without this, the dashboard looks like a foreign tool. A catalog manager checking MRP across 10 variants who sees "1999" vs "2499" vs "14999" has to do mental arithmetic that ₹1,999 / ₹2,499 / ₹14,999 eliminates instantly.
Fix Add a global `formatINR()` utility that formats all monetary values with the ₹ symbol and Indian number grouping. Apply to every price display in the product list, product form, variant table, and bulk import preview. This is a 2-hour engineering change with outsized trust impact.
🚦
Channel readiness has no single summary — sellers check three tabs instead of one status
SCREEN: Product Detail · Channel Simulator
Medium
The channel simulator requires the seller to select Amazon, then Flipkart, then Meesho separately and read three results. A product may be ready for Flipkart but blocked on Amazon. The current tab-per-channel design hides this cross-channel view. A seller preparing for a Flipkart flash sale shouldn't have to mentally track which channels are clear and which are blocked across three tab switches.
Fix Add a "Channel Readiness Summary" bar at the top of the product page — visible without opening the simulator. Three inline badges: Amazon [✓ Ready / ⚠ 2 warnings / ✗ 3 errors], Flipkart [...], Meesho [...]. Clicking a badge opens the full simulator pre-filtered to that channel. The summary should be computed on save, not on demand.
🔧
Bulk edit preview shows "affected count" but no sample of what actually changes
SCREEN: Bulk Edit · Preview Step
Medium
The bulk edit preview returns "affected count + sample set". The spec says "preview confirms affected records before apply." If the preview shows "482 products will be updated" with a list of names, a seller still cannot verify correctness — they need to see the before/after diff for at least the first 5 records. "482 products: title will change from [old] to [new]" is the verification step. Without it, sellers will accept previews blindly, leading to bulk mistakes they then need to undo via the history log.
Fix Preview must show a before/after diff table for the first 5 affected records. Each row: [SKU code] | [field name] | [current value → new value]. A "Show all 482" secondary link expands the full list. This pattern, borrowed from database migration tools, turns a scary "apply to 482" confirmation into a verifiable action.
🔐
RBAC role indicator is missing — viewers don't know they can't edit until they try
SCREEN: All screens · Role = viewer
Medium
The RBAC implementation correctly hides write controls for viewers. But the spec says "write controls hidden/blocked for viewer" — hidden is the right choice, but without a role indicator in the navigation, a viewer who has been given access to check a listing will wonder if the product page is broken because they can't find any edit button. They will file a support ticket or ask an admin. The role should be explicit and persistent in the UI.
Fix Show the current role as a persistent badge in the navigation bar: "Viewing as: Editor" or "Viewing as: Read Only". For viewer role, add a tooltip on hover of any disabled area: "You have view-only access. Contact your account admin to request edit permissions." This eliminates a category of confused support requests.
📱
Empty states and loading states are unspecified — likely blank white screens
SCREEN: Product List · Bulk Import · Channel Simulator
Low
P1-US-006 acceptance criteria specify "Empty and error states are implemented." The Phase 1 implementation doc doesn't confirm what these look like. Based on standard Next.js + shadcn patterns, they are most likely a default empty state (blank area or generic "No results") and a white flash during loading. For a product catalog tool, an empty product list on first login should guide the seller to their first action: Import your catalog. An empty channel simulator should explain why it's empty (no product selected).
Fix Design three states for every major surface: empty (first-time or no-results with clear CTA), loading (skeleton screens, not spinners), and error (what went wrong + what to do next). For the first-login empty state: a persistent "Get started" guide with three steps: (1) Create your first product or import a CSV, (2) Map to your channels, (3) Check your rejection risk.

Designer's Verdict

PIM1's UI is at the "developer-built v1" stage: the right data is on the right screens, the core flows are functional, and the technical implementation is sound. But it is built for engineers to validate — not for catalog managers to operate under pressure.

The gap between current state and "seller tool" is not a redesign. It is 10 targeted improvements, most under a day each. The biggest ROI items are: INR formatting (2 hours, instant trust), plain-language error messages (4 hours, eliminates a category of confusion), and live import progress (1 day, prevents the most common stress moment in the primary workflow).

Before onboarding real sellers — which the review has flagged as the most urgent business priority — the top 6 items from this list should be resolved. A real catalog manager's first session will expose every one of these gaps within 15 minutes. The technical foundation is strong enough to hold the weight of a real user. The UI surface is not yet.
